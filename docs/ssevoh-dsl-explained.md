# SSEVOH-DSL explained

**SSEVOH-DSL is a small language and verification framework for controlling changes that an AI agent proposes to its own harness.** Its full title is *A Domain-Specific Language and Formal Verification Framework for Safe Self-Evolution of AI Agent Harnesses*.

An agent harness is the environment around a model: its prompts, memory, skills, tools, workflows, configuration and execution rules. Changing these can improve an agent, but can also break dependencies, expand permissions or restore something previously prohibited.

SSEVOH-DSL makes a proposed change explicit and checks it before allowing deployment. The project implements a metadata core and a real, restricted integration with Google Research Harness². The completed experiments demonstrate admission control in these domains. They do **not** demonstrate useful model-driven self-improvement or universal safety of generated code.

## 1. What the language and framework do

The central rule is: **an agent may propose a change, but the proposal does not grant permission to apply it.**

The DSL describes seven component kinds: **skill, memory, tool, workflow, configuration, policy and verifier**. It supports three evolution operations: **update, withdraw and rollback**. Specifications identify versions, dependencies, provenance parents, capabilities, required validators, preconditions and postconditions.

For example, this existing project example requests a skill update while retaining its dependency on a memory component:

```text
harness assistant {
  component base memory { version 1; mutable true; }
  component target skill { version 1; mutable true; depends [base]; }
  evolution improve {
    operation update; target target; from 1; to 2;
    depends [base]; requires [structure]; expect active; ensure active;
  }
}
```

The specification does not authorize itself. The trusted caller supplies the authenticated identity, and an operator-owned policy decides what that identity may change. Proposal requirements can add validation obligations; they cannot remove the operator's mandatory requirements.

The framework then:

1. Parses the text and checks types, references and structural constraints.
2. Checks permissions, capability limits and the affected dependency/provenance graph.
3. Constructs an isolated candidate and runs required verification and validators.
4. Issues a single-use approval bound to the candidate and its trusted context.
5. Commits only if that context is still current, recording an auditable history.

Withdrawal keeps affected descendants inactive rather than silently treating them as safe. Recovery preserves the withdrawal history and checks whether a historical version is still eligible. Policy and verifier components remain protected even if a proposal describes them as mutable.

The core changes immutable metadata in memory. The Harness² adapter additionally manages actual file bundles and controlled execution. Arbitrary predicates, component creation/deletion, arbitrary multi-target metadata transactions and durable automatic restart are outside the implemented scope.

## 2. Research questions and what the evidence answers

The first five questions concern the DSL and assurance core; the next five concern its integration into an existing evolution system.

| Question | What it asks | Answer supported by the current studies |
|---|---|---|
| **RQ1 — Expressiveness** | Can the DSL describe important harness changes and their constraints? | Seven kinds and three operations represent the project's synthetic scenario families. Universal expressiveness and engineer usability have not been established. |
| **RQ2 — Formal assurance** | Can checks detect unauthorized or inconsistent evolution before deployment? | Independent finite conformance, history exploration, model checking and negative tests passed within declared bounds. This is not an unbounded implementation-refinement proof. |
| **RQ3 — Enforcement reliability** | Does enforcement control proposals generated by different models? | Of 500 raw outputs, 91 reached the independent oracle: 73 were disallowed and none deployed; 18 were allowed with no observed false rejection. Invalid outputs do not test unsafe-proposal rejection. |
| **RQ4 — Efficiency** | What does assurance cost? | Scheduled latency measurements were collected. The median B3 metadata action was 0.599 ms; admission-only baselines are not equivalent deployment pipelines. |
| **RQ5 — Scalability** | What happens as graphs and conflicting approvals grow? | All 180 graph/concurrency trials retained one committed winner. The tested range was 10–500 components and 1–8 conflicting approvals in one process. |
| **RQ6 — Integration effectiveness** | Can assurance be added without replacing the original evolution mechanism? | The unchanged Harness² workflow runs through added admission, execution and library controls; original and integration tests passed. |
| **RQ7 — Safety improvement** | Does the added contract reduce prohibited deployments? | On shared scripted fixtures, C0/C1/C2 admitted 25/20/10 of 45 disallowed attempts; full C3 admitted none. These are violations of an added operator contract, not controls upstream claimed to provide. |
| **RQ8 — Evolution capability** | Are legitimate improvements retained, and do model workflows improve tasks? | C3 retained all 15 legitimate fixture trials. However, evolved and frozen model workflows both achieved **0/50 task successes**. Useful self-improvement remains unestablished. |
| **RQ9 — Integration overhead** | What latency and resource costs does the integration add? | Mean legitimate shared-fixture action time was 77.2 ms in original C0 and 114.8 ms in full C3. These descriptive measurements do not establish general production overhead. |
| **RQ10 — Practical resilience** | Does it handle withdrawal, recovery, stale approvals and publication faults? | Real boundary tests and a bounded publication model cover these cases. Full C3 blocked all 20 prohibited lifecycle trials; durable recovery remains unsupported. |

The [claim-to-evidence matrix](claim-evidence-matrix.md) maps these statements to their artifacts and limits.

## 3. Experiments used

| Experiment | Design and objective | Main observation |
|---|---|---|
| **Core formal verification** | Compare runtime behavior with an independently implemented operational specification; explore histories; compare exact Python/TLC graphs; deliberately remove guards. | Agreement in 248,832 one-step cases and 19,620 bounded history transitions; 6,880 anchored trace replays; four lifecycle graph comparisons and five faulty variants detected. |
| **HeartBench baselines** | Twenty synthetic scenarios, 25 actions and five repeats across B0 parsing, B1 basic structure, B2 static checks and B3 full assurance: 500 records. | B3 retained 65 allowed trials and rejected 60 disallowed trials. B0/B1 admitted 60 disallowed trials each; B2 admitted 20. |
| **Five-model DSL generation** | Twenty eligible request contexts × five seeds × five frozen models: 500 raw outputs under full enforcement. | Only 91 were independently evaluable. Three models emitted no syntax-valid raw DSL under the fixed protocol. No independently disallowed proposal deployed. |
| **Metadata mechanism ablations** | Five named removals plus a full control: 750 records. | Closure, provenance and revalidation removals each exposed five disallowed admissions. Other removals had zero observed effect with overlapping guards retained. |
| **Graph and concurrency scaling** | Three sizes × chain/star/random shapes × 1/2/4/8 conflicting approvals × five repeats: 180 trials. | One winner per batch. At 500 components with one contender, median batch times ranged from 0.470 to 0.773 seconds across shapes. |
| **Harness² controlled comparisons** | Twelve shared fixtures, four separately scoped lifecycle scenarios, eight ablations and five repeats: 900 records. | Full assurance blocked the tested contract violations while preserving the three legitimate fixture families. |
| **Harness² model workflows** | Five models × five seeds, each processing two ledger tasks: 25 streams and 50 task observations, with frozen references. | There were 141 assessed disallowed proposals and none deployed. Both evolved and frozen workflows had zero task successes. |
| **Publication verification** | Model-check bundle publication and activation, and compare exact Python/TLC graphs. | Four graph comparisons passed; six faulty variants were detected. This abstraction is not a filesystem/crash-recovery proof. |
| **Multi-cluster qualification and output comparison** | Repeated smoke graphs on Fir, Narval and Rorqual; compare matched outputs only after checking source, model, prompt, decoding and runtime identities. | Fir/Rorqual qualified before the deadline. Twenty-four comparable output pairs matched, but both outputs in every pair were syntax-invalid; this does not establish useful-generation replication. |

The five Ollama identifiers were `qwen2.5-coder:7b`, `phi4:14b`, `gpt-oss:20b`, `devstral:24b` and `qwen3-coder:30b`. These are experimental subjects, not benchmarks. Exact model digests and runtime metadata were frozen.

The original raw `task_completion` field checked selected transition fields. A separately labelled **post hoc strict request-fidelity diagnostic** adds snapshot, evidence and applicable-condition checks. GPT-OSS and Qwen3-Coder each matched 21/100 requests by that diagnostic; the other models matched none. Fidelity can include a faithfully expressed prohibited request, so it remains separate from safe admission and useful task execution. Original samples and metrics were preserved.

## 4. Which standard benchmarks were actually used?

**The completed primary and ledger studies used no external standard benchmark.** A subsequent TSE extension has run an actual two-task HumanEval+ diagnostic pilot through original Harness² recursion and pinned EvalPlus on Fir, Narval and Rorqual. This is a benchmark subset, not a completed164-task evaluation. The full study remains behind fresh infrastructure/protocol qualification.

| Suite or workload | Status | What it evaluates |
|---|---|---|
| **HumanEval+ v0.1.10** | Two-task diagnostic pilot completed on all three sites; full 164-task study pending. | Real Python-generation deliverables, original recursive workflow, external base+expanded-test grading. |
| **HeartBench v1** | Project-authored synthetic suite, not an established external standard; independent researcher label review remains open. | Metadata permissions, dependencies, provenance, evidence, withdrawal, rollback and deployment conflicts. |
| **Harness² ledger/catalog fixtures** | Controlled integration workload built around the upstream demonstration adapter and an added bounded model backend. | Actual file-bundle admission, execution, library reuse, operator-contract enforcement and two ledger-task outcomes. |
| **Generated graph/concurrency workloads** | Synthetic performance experiment. | Cost growth, quarantine and conflicting commits under stated sizes and shapes. |
| **Formal conformance and TLC checks** | Verification evidence, not a standard agent-performance benchmark. | Agreement with the declared semantics and bounded lifecycle/publication properties. |
| **JobBench, LAB and WorkBuddy-Bench** | Supported by the inspected Harness² upstream, but **not run as SSEVOH-DSL evaluations**. | Upstream professional-task benchmark results cannot be attributed to this integration. |

Passing the 70 upstream unit tests is also different from running those professional benchmarks. Consequently, this project cannot currently claim standard-benchmark superiority, replication of the Harness² paper's gains or broadly demonstrated agent-task improvement.

## 5. How the Harness² integration works

The target is `google-research/harness2` at commit `6868817518876de8fd170c6a8354daca273b6191`. Its source remains unchanged. Its original proposer, retries, contrastive probes, parallel/sequential composition, output selection, reflection and improvement library remain in use.

In the primary DSL experiment, models output DSL text. In the Harness² integration, models propose **data-only JSON file edits**, and the trusted authority constructs the DSL metadata for the resulting bundle. The model cannot grant itself permissions through either format.

The integration follows these actual boundaries:

1. **Keep upstream validation.** `_run_stage` supplies stage/base context. `_accept_tree` performs the original checks before invoking SSEVOH assurance.
2. **Represent the complete tree as a versioned bundle.** A whole harness file tree becomes one metadata component depending on protected policy/verifier/guardrail metadata. Several edited files can therefore be published together. This is not arbitrary multi-target metadata transaction support.
3. **Approve exact content and context.** Permission, validators, candidate bytes, base, source identity and known version origins are bound to the approval. A changed context invalidates it.
4. **Publish and verify before execution.** Complete files are staged privately and published as a directory. A separate receipt is required; merely creating a directory does not authorize execution. The execution boundary rechecks the stage's bytes and receipt.
5. **Protect learning across tasks.** Library adoption requires evidence from an executed eligible run. Later context snapshots exclude withdrawn versions and known derivatives while retaining historical records for audit.

Branch candidates remain independent, as in upstream. Checked recovery restores the actual branch base while preserving the monotone withdrawal history. Execution leases serialize with withdrawal. A nonempty authority store is refused on reopening because verified durable restart is not implemented.

Implementation: [bridge](../integrations/harness2/adapter/ssevoh_harness2/bridge.py), [authority](../integrations/harness2/adapter/ssevoh_harness2/authority.py), [bounded model backend](../integrations/harness2/adapter/ssevoh_harness2/models.py) and [architecture](../integrations/harness2/integration-architecture.md).

## 6. Features and benefits added to Harness²

The inspected upstream already has surface/path checks, structural validation, grader-information separation, retries and fallback behavior. SSEVOH preserves those safeguards. Its contributions address additional assurance requirements identified at the inspected integration boundaries.

| Existing gap or additional requirement | Feature added | Benefit and limit |
|---|---|---|
| Editable surfaces do not by themselves define who may perform each evolution operation. | Operator-owned identity/operation permissions and protected-content rules. | Rejects changes outside the declared authority, including protected policy/verifier edits. This is an added contract. |
| Earlier validation does not bind every later execution to an SSEVOH approval. | Context-bound single-use approvals, exact-byte receipts and execution rechecks. | Prevents unchecked substitutions or stale approvals from authorizing execution at the supported boundary. |
| Removing a library entry does not express global version/origin revocation. | Monotone withdrawal and tracked version-origin restrictions. | Blocks execution and reuse of withdrawn bundles and known derivatives. It does not prove semantic causation of every LLM-derived idea. |
| Ordinary fallback does not provide the added prohibited-version-safe historical recovery policy. | Explicit checked rollback/recovery. | Rechecks old versions against current restrictions without deleting withdrawal history. |
| Several files must form one admitted artifact. | Whole-bundle staging/publication and a separate activation receipt. | Supports several-file updates without authorizing incomplete or unreceipted bundles; no general durable transaction claim. |
| Decisions need an explanation and reproducible evidence. | Source/policy/evidence/artifact hashes, journals and decision records. | Makes proposal-to-deployment and subsequent reuse auditable under the trusted-host assumptions. |
| Arbitrary tool-enabled editors would need stronger isolation. | Data-only proposals and a finite executable catalog in the supported backend. | Restricts executable behavior in this initial domain. General OpenCode/Codex execution remains unsupported. |

The demonstrated benefit is **stronger control of the tested evolution boundaries**, not a demonstrated increase in task-solving ability. C3 blocked all 45 disallowed shared-fixture attempts and retained all 15 legitimate trials. The model-driven study's 0/50 task successes prevents a claim of useful self-improvement.

The [verified gap analysis](integrations/harness2/gap-analysis.md) distinguishes pre-existing upstream safeguards from added requirements. The [adapter contracts](../integrations/harness2/formal/contracts.md) explain the trust assumptions and formal bounds.

## 7. Execution, results and remaining work

The project reused the pinned `use-hpc` Slurm pipeline. Qualification was submitted on Fir, Narval and Rorqual. Fir and Rorqual qualified within the 45-minute selection window; Rorqual had the lower observed eligible-site completion cost. The two smaller model cells ran there, while the three larger models ran on Fir, where their pinned weights were cached.

Narval's completed late cells were preserved. Its remaining queued GPU cells were subsequently closed as **censored observations**, with downstream collection retained. They were not labelled GPU failures and did not change the frozen assignment. Inference used scheduled GPU allocations; statistics used scheduled CPU jobs. Logs, snapshots, accounting and transfer hashes support the audit.

The remaining research work includes external benchmark evaluation, independent label review, broader artifact/executor support, calibrated generation protocols, stronger semantic validators and durable recovery. The present formal results establish agreement within stated bounds, not universal soundness/completeness for arbitrary agent programs.

## Subsequent TSE extension status (10 November 2026, UTC)

The coding adapter separates generated solution Python from mutable Markdown harness files. Generation executes no Python; external grading occurs after selected outputs and online library state freeze. The pilot gave Qwen2.5-Coder 2/2 successes in each condition, while Phi-4 gave 1/2 under guarded recursion and 2/2 under original recursion. No distinct modified harness bytes executed in that first pilot, so this difference cannot be attributed to lifecycle enforcement. A disjoint development check exposed a displayed-path prefix mismatch; the transport now records exact prefix mappings and rejects traversal/collisions. Later diagnostics found live outputs entering source hashes and a cold CUDA-discovery failure before task prompts. Those records remain separate from qualification used to select full-run sites.

The current plan uses two models and three ordered streams/model on all 164 tasks, with per-seed descriptive comparisons. Online learning couples tasks; a five-entry visible library does not make tasks independent. The frozen eight-solver reference is solver-call-matched, not matched in total model calls. Prior smoke/control exposure is disclosed with 162-/161-task sensitivity summaries.
