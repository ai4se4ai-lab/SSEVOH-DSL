# Adapter assurance contract

The checked core is unchanged. The integration treats a complete Harness² file tree as one versioned metadata component, depending on immutable operator-policy, verifier and guardrail components. A multi-file bundle update is one core update, not an implementation of arbitrary multi-target metadata transactions. Branches are retained as separate historical bundle versions; switching to an earlier branch uses checked recovery and retains the current withdrawal set.

The operator owns the Python process, initial catalog, policy, validators and store. The untrusted model can only return bounded JSON/text edits. It has no tools, filesystem handles, Python object references, validator registration or caller-identity control. The supported executors are the exact upstream DemoAdapter and the added bounded ModelAdapter. Both invoke only scripts whose AST matches the two explicitly enumerated catalog programs. The bounded model can request that fixed tool or return text, with no arbitrary command facility. An agent with arbitrary shell/process access is outside this supported threat model; broader executors are rejected rather than represented as isolated.

Approval binds source/IR through the core token and exact artifact bytes and extra exposure origins through the authority's immutable pending record. Published receipts retain both bindings; library receipt replacement is rejected. Policy and all imported core/upstream/adapter source files are re-attested before preparation, commit and execution. Protected paths cannot change. Surface/dependency/schema checks and the finite code catalog are independent required validators; LLM explanations do not supply evidence. Known fallback lineage and all declared library and candidate-pool exposure origins are retained. Exposure is conservative, not a proof of semantic contribution.

A new directory containing every file and a content manifest is prepared privately and atomically renamed. It does not become executable merely by existing: a separate publication receipt is required after core commit and trace recording. The authority lock covers preparation/commit/registry visibility and execution. A failed staging step exposes no candidate. A trace/publication failure cannot publish a valid execution receipt; if metadata already advanced, checked recovery restores the previous content while retaining the failed attempt in history. Revision/audit history can therefore advance on compensated failure. No durable multi-resource transaction or automatic crash recovery is claimed. Reopening a nonempty store is refused, so a restart cannot silently forget withdrawals.

Execution re-reads the mutable upstream stage tree, checks its task/stage-specific receipt and exact hash, checks current withdrawals and exposure origins, and copies the verified immutable catalog files into an execution lease. The lock is held until the real subprocess exits; withdrawal cannot race an active lease. After a version or source is withdrawn, new execution/adoption is denied. Library context is rebuilt from registered, untampered, active receipts; quarantined histories remain on disk. Original upstream selection, reflection and no-grader rules remain in force.

Induction over successful authority operations: initial catalog/schema/graph are checked; prepare adds no published receipt; commit publishes only bound verified complete bytes under unchanged context; execution requires an active receipt and a good copy; withdrawal monotonically adds prohibited identities and invalidates their known descendants; recovery retains current prohibitions. These preserve receipt-before-execution, protected policy, byte binding and withdrawal safety under the stated assumptions.

Machine evidence comprises actual upstream/integration/security/fault tests plus a finite publication abstraction checked by both Python and TLC with exact state/labelled-edge agreement. The model covers one new bundle, one origin-revocation bit and policy epochs zero/one; execution leases prevent concurrent withdrawal/tampering transitions. Six negative variants remove authorization, evidence, all byte binding, context revalidation, activation withdrawal checks or publication-receipt checks and must produce counterexamples. This is not a mechanized refinement theorem for all Python/filesystem executions. The core's separate 248,832 one-step and 19,620 history cases retain their original bounds.
