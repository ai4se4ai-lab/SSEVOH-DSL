# Integration architecture and acceptance conditions

No executable integration boundary exists in the pinned survey companion. This document defines the constraints to apply after identifying an executable upstream; it does not describe an implemented adapter.

Preserve the original proposer, experience processing and candidate search. Intercept a fully formed candidate before its first write to trusted runtime state. Snapshot all actual component/artifact identities, dependencies, version origins, installed generation and operator policy. Translate that snapshot and proposed effect to the supported DSL. Any requested creation/deletion or several-component transaction must first receive explicit semantics, a core extension and renewed formal checks; sequential single-target commits cannot be called one atomic transaction.

A separately protected assurance service owns policy, validators, approval state and deployment access. The evolving agent receives no filesystem permission to those objects and cannot replace that service's executable or adapter. Hashes support detection and binding but do not themselves enforce OS access control. Validators run against isolated candidate artifacts and declared environments. LLM text is a proposal, not evidence. Missing or failed checks must fail closed.

An integration decision must include an evolution ID, APPROVED/REJECTED/REQUIRES_REVALIDATION/INSUFFICIENT_EVIDENCE/VERIFICATION_FAILED, policy and specification versions, verification/evidence references, reasons, timestamp, and source/candidate/environment fingerprints. The current core supplies the checked approval or categorized exception; the future adapter must map these faithfully and never turn errors into approval.

The deployment adapter must bind the approved metadata to exact artifact bytes and a checked installed generation, then atomically publish the complete validated candidate where the target's storage permits it. A metadata swap alone does not publish files or containers. If underlying installation is non-atomic, its staging/recovery protocol needs its own model, fault tests and documented limits before trusted execution. A later run must load the exact admitted artifact and record available/reached/carried evidence in the scored trajectory.

Acceptance requires genuine C0 execution from the unchanged upstream, correct interception before writes, authenticated caller identity, checked mapping of every actual mutation, invariant-preserving deployment, independent verifier protection, reproducible recovery, concurrency/conflict checks, and the ten plan scenarios. Only then can C0–C4 and eight sandbox ablations use the existing three-site HPC orchestration. At present these acceptance conditions are unmet because there is no upstream runtime to bind.
